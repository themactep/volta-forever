# Changes

## Unreleased

### Fixed

- The CUDA 13.5 cuBLAS half GEMM runs on a V100 without the CUDA 12.9 forwarder: the kernel
  cuBLAS selects (`turing_fp16_s1688gemm_fp16_128x256_ldg8_relu_f2f_stages_32x1_nn`) translates
  and runs, and all 65,536 outputs of the probe's 256×256 GEMM are the CPU reference's
  (`tests/gpu/run.sh`, `runtime-13.5-ptx`); an RTX 3060 run of the same probe, natively, gives
  the same. Turing's zero-fill loads (`Pnz`) become a load under the predicate and `RZ` moves
  under its complement; `F2FP.PACK_AB` (two f32 to two f16 in one register, which the sm_75
  description has and NVIDIA's disassembler prints for SM80 only) becomes two `F2F.F16.F32` and
  a `PRMT`; the sm_75 cache/scope table of a rebuilt load is sm_70's, and a changed load names
  no batch. A kernel entered from outside may use the registers above the ones it names when
  level 3 would otherwise refuse it, and a kernel that does not use R1 gets its frame from the
  top of the thread's local memory. The independent validator learned the F2FP and zero-fill
  sequences, the return address of a `LEPC` call, and that `BRA.U`'s `cond=1` is the uniform
  modifier, not a condition. Six `turing_fp16_s1688gemm` 128x128 variants and the image's
  CUTLASS GELU kernels (for `MUFU`) are still refused (`LIMITS.md`, "Kernels refused").
- A direct call whose return address is the program counter read by a `LEPC` immediately before
  it (cuDNN 9.24's sm_75 kernels give direct calls so: `LEPC R128; CALL.REL`) was refused with
  `LEPC ... without a call after it`. It is translated now: the `LEPC` and the call move with the
  code, so the return address needs no number fixed up. In one cuDNN 9.24 library, 311 of the 312
  functions of the cubin that held the refused down-sample kernels were refused; all 312 translate,
  and the CUDA 13.5 cuBLAS `volta_sgemm` kernel runs (`tests/gpu/run.sh`, `runtime-13.5-ptx`).
  The callee decides whether an adjacent `LEPC` is the call's return address: when every `RET`
  it can reach is `RET.ABS` on the `LEPC`'s register adding `0x20` and nothing of it writes that
  register, the pair is the return address and **no `MOV` of the same number is fixed** (it may
  be data; a cuDNN function has one); otherwise the call is an ordinary one and exactly one `MOV`
  of its return address, before it and reaching it in a straight line, is fixed, as without a
  `LEPC` — none or several are refused. The scheduler's fillers must not come between an
  accepted pair; the translation refuses if they do. The validator checks each accepted pair by
  itself (the `RET.ABS` register and immediate, no writes, no branch at the call) and that the
  pair stays adjacent with the `LEPC` unchanged; it no longer objects to an adjacent `LEPC` whose
  callee returns another way, which is an ordinary call. `LEPC Rd` writes the 64-bit pair
  `Rd:Rd+1` and `RET.ABS Ra` reads it: a callee that writes either half does not return through
  the pair, and a guarded `RET.ABS` is only one way out (its fall-through must return through the
  pair too). Only an accepted pair exempts its `LEPC` from "without a call after it", as on
  `main`. `tests/kernels/translate/k_lepc.cu` and its checked-in cubin (the shape made from
  nvcc's `MOV` and `RET.REL` by `make_lepc_cubin.py`, in a register pair its callee leaves alone)
  carry the pair for the unit tests, `compare.sh` and `controls.sh`; `tests/kernels/k_lepc_upper.sm75.cubin`
  is the first build, whose callee writes the upper half, kept as the refused case. The controls
  `lepc_not_adjacent` and `lepc_register_changed` are objected to on the pair. The
  independent validator first reported 1,040 "gives a predicate back" problems
  in the newly translated cuDNN functions; they were its own rule counting `RZ` (255) as a
  register of the translation (below).
- `reference/validate.py` took an `R2P` that restores predicates from `RZ` for one of the
  translation's restores: `RZ` is 255, above every register, and the rule identified a register
  of the translation by "above the highest". cuDNN 9.24's sm_75 kernels have such `R2P`s (clear
  predicates); the validator reported 1,040 problems on a translation that the two translators
  agree on. `RZ` is not a register of the translation; with it excluded, the 312-function
  cuDNN 9.24 cubin checks with 0 problems.
- PTX, cubins and fat binaries given to the driver's linker in files (`cuLinkAddFile`, `cuLinkAddFile_v2`) went to the driver as they were, where the same bytes given in memory (`cuLinkAddData`) are adapted: on a V100, NVIDIA's driver refuses a file of PTX for sm_75 made by CUDA 13.5 (222, `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`) and one of relocatable sm_75 machine code (209, `CUDA_ERROR_NO_BINARY_FOR_GPU`), and links a fat binary of sm_75 machine code and PTX into an image without its kernels. The layer now reads such a file and gives the driver's `cuLinkAddData` what it makes of it, as of the same bytes in memory; its kernels that cannot run are refused at their lookup in the image that the link makes, with their line. The driver is given the file itself when nothing in it is adapted, when it cannot be read, and when the driver refuses what the layer made of it; a file of another type (a host object, a library of them) is not read, as such an input in memory is not (pull request #18, by midhatn). What is still not carried through a link, in memory or in a file, is in `LIMITS.md` ("Kernels refused"): a kernel whose code is a trap and nothing else, and a call into a function of another input that cannot run.
- A function of sm_75 machine code with `UIMAD` of an immediate addend (`UIMAD UR4, UR4, UR5, 0x240`), or with a carry in (`UIMAD.X`, `UIMAD.WIDE.X`), was refused, and with it its kernel ("no translation for uimad__URURsI_URURI (UIMAD)": issue #8, of exllamav3's `exl3_moe_kernel`). These forms now become `IMAD`, `IMAD.X` and `IMAD.WIDE.X` on the ordinary registers that stand for their uniform ones (pull request #15, by midhatn). In the held-out corpus, at the default setting, 691 functions of 152 cubins are translated that were refused (cuBLASLt 293, cuSPARSE 112, cuFFT 101, cuSOLVER 73, NPP 61, cuBLAS 35, cuDNN 8, vLLM's compiled extension 6, cuRAND 2), and no function that was translated before is translated otherwise, in the 11,620 cubins of the corpora and of the tests at ten settings of the translator; 51 functions of 9 cubins that were refused for `UIMAD` are still refused, for the next form they hold that has no rule (38 `UPRMT`, 6 `UPOPC`, 4 of the class `lea_hi_noimm_sx32__RUR_RUR`, 2 `UFLO`) or for a call's return address (1). The kernels of issue #8 were not at hand: what they meet after `UIMAD` was not seen.

## 0.1.6 (2026-11-25)

### Fixed

- In a program whose code is PTX only, for an architecture after Volta's (a CUDA 13 build for `75-virtual`, as Ollama's `cuda_v13` runner is), the device-wide algorithms of CUB and Thrust (sorts, reductions, scans) failed with "invalid device function": the PTX version of a kernel of the program (`ptxVersion` of `cudaFuncGetAttributes`, `CU_FUNC_ATTRIBUTE_PTX_VERSION`) was the 7.0 of the PTX that the layer retargets for the V100, and CUB of CUDA 13 chooses by it among the architectures that the program was built for, of which 7.0 is none. ggml's ARGSORT over more than 1,024 columns stopped there (`CUDA error: invalid device function`); its TOP_K, CUMSUM, SUM and MEAN take the same calls, and on 0.1.5 llama.cpp v1.0.0 built so stopped in CUB's top-k with `-bs` and with `draft-mtp` and its default backend sampling of drafts (an outside report, issue #4). Through this change, the ARGSORT (up to 1,048,576 columns), TOP_K, CUMSUM, SUM and MEAN cases of llama.cpp b11521's `test-backend-ops`, built so, pass; and in the tester's run with this change, the same llama.cpp v1.0.0 build ran with `-bs` and with `draft-mtp` and its default backend sampling of drafts to the end, and its other runs gave the tokens of 0.1.5, with the same log-probabilities of the five first candidates at every position where they were read (`docs/reports/`). A function or a kernel whose code the layer retargeted from PTX for a later architecture is now said to be compiled from that PTX, as a GPU of that architecture or a later one says it, at most the capability that its caller is told (told 8.0 with `VF_CAPABILITY_ALL=1`, code from PTX for sm_75 is answered 7.5, and 8.0 for its machine code); the machine code's answer is the capability told, as before. Through modules and libraries, loaded from memory or from a file, deferred libraries and their kernels compiled alone, the module of a library in a context, the layer's cache, and on a later card in the same machine for the layer's code there. A caller with code of its own for the V100, or a launcher client without GPU code, is answered what the driver answers; translated machine code keeps the architecture of its PTX in its header, as it did. The proxy's cache has a new format (the architecture is in the manifest of a deferred library): the first start after the upgrade adapts again.
- The CUDA 13 build of NCCL (the `nvidia-nccl-cu13` 2.30.7 that PyTorch 2.14 and SGLang 0.5.23 install) could not run a collective on a V100 (issue #2). The layer refused 41 of the 53 kernels of its device-linked image and 18 of its 82 kernels for symmetric memory, for multicast instructions (`multimem.*`). Its ring and tree kernels hold these behind tests that only its NVLink-SHARP transport passes, or may reach them through its table of functions. The PTX manual leaves these instructions undefined without a multicast address, which no V100 can have (the driver answers 0 to `CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED` and 801 to `cuMulticastCreate`). Where the driver says that no GPU of the process can take part in multicast, the layer now replaces each such instruction, not its function, by a reported trap (a call of `__assertfail` that names the instruction and the function, then `trap`), and gives the kernels. None of the 53 is refused now. Of the 82, only the 17 that copy with `cp.async.bulk` are, which NCCL 2.30 chooses on sm_100 and later only. On two V100s, `torch.distributed` collectives with the wheel's NCCL gave the CPU's values exactly, floats included, with NCCL's own choice of algorithm and protocol and with each of Ring and Tree in Simple, LL and LL128 (`tests/gpu/nccl.sh`), and SGLang `--tp-size 2` gave the CPU's greedy tokens. The first start compiles NCCL's adapted code (248 MB of PTX) for about 15 minutes in each process, and the layer says so before the driver begins. The driver's cache keeps the 383 MB it makes; its default limit of 1 GiB holds them, though other programs' compiled code shares that cache (`CUDA_CACHE_MAXSIZE`). Later starts take about half a minute more than with the CUDA 12 build (`vf fetch --only libnccl`), which stays the faster start (`LIMITS.md`, "Several GPUs and NCCL").
- The line that names NCCL's CUDA 12 build as the remedy came with the first refused kernel of NCCL's, whichever it was. It now comes with a refused kernel of NCCL's collectives (`ncclDevKernel_`, `ncclKernel_`), and not with one of its kernels for symmetric memory, which NCCL goes on without.

- After a kernel faults (an illegal address, a misaligned access, a `trap`: errors 700, 716, 719 and the others of their kind), the first call that the layer routes and that returns the error in a context makes the layer say, once and at every log level, which kernels may be the one: those launched in that context since their last synchronisation that succeeded, the last first, each with its grid, block, stream and thread, what the layer made of its image (as the program gave it, PTX retargeted, the PTX of a cubin retargeted, machine code translated and whether its tensor-core products are computed in pairs, compiled alone or with its whole module, from the layer's cache, launched from its second translation), the size and XXH64 of the image given to the driver and the program's image as its load named it; a CUDA graph's launch with the kernel nodes captured in it; and how to know more. The lines never say that a kernel faulted (a copy or a memset, which the layer does not see, may be what failed); 214, 220 and 911 are said to be errors of the hardware, with what ran then.

## 0.1.3 (2026-11-23)

### Fixed

- Machine code translated from sm_75 could store wrong values when a store of a register came just before an `ldmatrix` into that register: the translation wrote the load's destinations before the store had read them. Triton's fp32 `tl.dot` kernels gave wrong results, different from one run to the next, at the default settings. Present in 0.1.2 and earlier.
- With `VF_CAPABILITY` at 8.0 or more, PyTorch computed wrong results with no error, and from 9.0 faulted the GPU: it chose kernels that its sm_75 machine code has only as stubs. Callers are now told no later generation than the code they are given (PyTorch, cuDNN, cuFFT, cuSOLVER and the CUDA runtime they use: 7.5), with a line that says so; a program whose code is PTX for the generation asked is told what was asked, as before. `VF_CAPABILITY_ALL=1` restores the old answer.
- With `VF_CAPABILITY` at 8.0 or more, what a caller is told is lowered until the code given for it lowers it no more: given PTX for sm_75, it is told 7.5; given PTX for sm_80, or the PTX that sm_80 cubins retain, at most 8.0; given PTX for sm_90, at most 9.0. A program told 7.5 is given the sm_75 code of every image it loads, no longer sm_80 code (the PTX that sm_80 cubins retain, or the sm_80 PTX of another fat binary of its file).
- With `VF_CAPABILITY` at 8.0 or more, a CUDA runtime is told no later generation than the code of the libraries that use it, also through a library of theirs without GPU code, and at most 7.5 when one of them has code for sm_70. A library without GPU code of its own, beside libraries with GPU code that depend on it, is told at most 7.5 until they are loaded, then what their code allows. This general rule replaces one for cuDNN's graph library by its name; that library now follows the library of engines that the loader actually loaded.
- With `VF_CAPABILITY` at 8.0 or more, a caller whose file was replaced or removed after it was loaded is told at most 7.5.
- The capability told to a main program no longer depends on how it was started (by name through `PATH`, after a change of directory): the program is read through `/proc/self/exe`. Without `/proc`, it is classified by the path it was started by, as in 0.1.2, and its code also limits the CUDA runtime it asks through.
- The capability hooks no longer hold their lock over the loader's lock, which deadlocked a capability query made from a `dl_iterate_phdr` callback. A panic while reading a caller's GPU code sets no limit instead of ending the process.
- In a machine with a V100 and a later card, modules loaded into a context on the later card are given to the driver as the program gave them; a library (`cuLibraryLoadData`) keeps the entries of the other cards beside its code for the V100, and its kernels refused on the V100 are given in its module on the later card; `CU_FUNC_ATTRIBUTE_BINARY_VERSION` is changed to the capability told only for code on the V100.
- A refused or failed kernel lookup (`cuModuleGetFunction`, `cuLibraryGetKernel`) leaves NULL in the handle, as NVIDIA's driver does for a name it does not have, also in deferred libraries. A refusal is still error 218, also for a lookup that waited while its kernel was being refused (it was given the stub).
- Kernels that cannot run on the GPU, in the inputs of the driver's linker (`cuLinkAddData`), are refused at their lookup in the image that `cuLinkComplete` makes, with the reason: also in copies of it, when it is asked for without its size, and when it is put in a fat binary of the program's own or behind a wrapper of the CUDA runtime. Its kernels with emulated instructions are announced. They used to reach the program as code that traps.
- A module or library whose unload the driver refuses, and a link whose destruction it refuses, keep their refused kernels.
- `cuLinkAddData` reads a fat binary within the size given, and passes one of size 0 to the driver as it is; a link made with `CU_JIT_TARGET` for another architecture than the V100's gets its inputs unchanged; a library load with compiler options without values goes to the driver as it is.
- libnvJitLink.so.13: the kernels that trap in a link of which other kernels run are named in the cubin it makes (a `.note.vf.refused` note), and the layer refuses them when the program asks for them, wherever that cubin is loaded (as a cubin, from a file, as an input of the driver's linker, uncompressed in a fat binary or a wrapper). A fat binary in which every kernel traps (PTX, or relocatable sm_75 machine code) is refused, as such PTX given as text was; it used to be linked into a cubin of traps.
- PTX that a cubin retains (`-lineinfo`, `-G`) is compiled again with the contractions that its machine code made: an addition that ptxas did not fuse with a multiplication (`--fmad=false`, a debug build) is not fused by the driver's compiler either. A cubin of which that cannot be told (no line table) is not compiled from its PTX.
- A process made by `fork()` that ends with `exit()` no longer hangs in the reports at exit of the layer or of libnvJitLink.so.13; these reports (`VF_STATS`, `VF_PROFILE`, the summaries) are printed only by the process that loaded the library.
- When a context is destroyed (`cuCtxDestroy`, the last `cuDevicePrimaryCtxRelease`, `cuDevicePrimaryCtxReset`, as on `cudaDeviceReset`), the layer drops what it kept of the modules of that context (adapted images, kernels, originals kept for a second translation, the second translations) instead of keeping them for the life of the process.
- Fixed races in which a module, library, link or context handle that the driver gives again, right after an unload, a link destroy or a context destroy, made the layer drop the records of the new load (its refused kernels were then given as code that traps) or give a kernel compiled for the previous load; the same in deferred libraries (an unload during a lookup, a lookup that waited across an unload and a reload) and in the second translation at launch. A second translation made for a module whose context was destroyed is no longer unloaded by its handle, and the release of a primary context decides whether it was the last before another thread's retain.
- A kernel of a lazily compiled library is given at once while another library restored from the proxy cache is being adapted, and a library restored from the cache is adapted once when several threads ask for different kernels of it at the same time.
- A write to the proxy cache that fails leaves no temporary file; temporary files left more than ten minutes before are removed at the first use of the cache, and one left by an earlier start of a container no longer makes a later write fail.
- An unload of a module waits for a launch from its second translation and for a setting given to it, instead of possibly letting them reach a function of another module.
- `cuModuleLoad` and `cuLibraryLoadFromFile` adapt a file whose path is not valid UTF-8.
- libnvJitLink.so.13: `nvJitLinkAddFile` opens the file by the bytes of its name; a name that is not valid UTF-8 was refused, or another file was linked in its place.
- A fat binary whose compressed entry announces an uncompressed size that no entry has (above 2 GB, or more than LZ4 can make of its bytes) is refused with an error instead of ending the program on a failed allocation; a zstd entry is no longer decoded past the size it announces. The proxy's cache reader no longer reserves more than its files can hold.
- libnvJitLink.so.13: `nvJitLinkCreate` with a null array of options, or a null option, returns `NVJITLINK_ERROR_INVALID_INPUT` instead of crashing; `nvJitLinkAddData` of no bytes or at a null address returns `NVJITLINK_ERROR_INVALID_INPUT` for every input type, as nvJitLink 12.9.2 does.
- `redux.sync` forms that the PTX ISA does not have (a sum of floats, bitwise operations on other types than b32, ...) make their kernel refused instead of being lowered; over a partial warp every lane reduces in the same order; a float `min` or `max` without `.NaN` over a single lane gives the canonical NaN for a NaN, as over several.
- With `VF_PROFILE`, each kernel keeps the counts of its first 64 distinct grid, block and dynamic shared memory sizes: a long-running program no longer makes the profile grow with every new launch shape.
- `vf ptxas`: ends with status 255 on the errors it finds itself, as ptxas; the assembler's messages name the user's input files instead of `/proc/self/fd/N`; `--apply-controls`, `--enable-func-clone-sc` and `--sanitize` take their value, and `-O` no longer takes the argument after it.
- The runfiles views that `vf` makes for a Bazel program are named by a fixed hash and kept under `runfiles-v2`. The program and every process it starts hold a lock on its view, and a view is removed only when nothing holds it, also across machines that share the cache over NFS; none is removed on NFS mounted with local locks or on FUSE. `runfiles-v1`, of earlier releases, is not touched.
- The launcher no longer takes a leftover of an interrupted NCCL download (`libnccl.so.2.vf-part`), or an empty `cuda-12.9.2/lib`, for the CUDA 12.9.2 libraries, which hid a toolkit found next; `vf doctor` says which CUDA 12.9.2 directory it took and why.
- `vf fetch` unpacks each archive and the NCCL runtime in a staging directory and moves them into place with a journal: a fetch that fails or is stopped leaves the previous files rather than a mix, and Ctrl-C, SIGTERM and SIGHUP stop it once the move it is making is done. After a SIGKILL or a failure during a move, the launcher refuses the directory with a message, `vf doctor` says so, and the next `vf fetch` completes the move; it also removes what an interrupted fetch left.
- `vf fetch` says which member an NCCL wheel lacks instead of ending with a Python traceback.
- Run under itself (`vf vf ...`, or after `eval "$(vf env)"`), the launcher no longer adds its `VF_AUDIT_MAP` entries again, and `vf --no-audit` (and `vf env --no-audit`) takes the layer's audit library out of an `LD_AUDIT` that already names it, which the loader otherwise loaded all the same.
- `install.sh` removes the staging directories that killed installers left more than a day before.

### Added
